Technical documentation

Language support that stays out of the way.

vscode-sfl turns .sfl files into a first-class language in VS Code. A thin client in the extension host starts a stateless language server, which parses the live document on every request and answers with diagnostics, completion, hover, navigation, rename and formatting.

Goals and principles

The extension is small on purpose. Each part has one reason to exist, and the language logic never depends on VS Code APIs, so the same server could be pointed at any LSP-capable editor.

01

Client spawns, server thinks

extension.ts only starts the server over IPC and registers it for the sfl language. All language logic lives server-side.

02

One parse per version

The document model is cached per file and keyed by the LSP document version. Diagnostics, completion, hover and the outline for one keystroke share a single parse. Versions only grow, so a version match is the whole invalidation story.

03

Self-contained parser

sfl-core/ is a ported copy of the SFL parser, extended with source ranges. The extension has no runtime dependency on stickyflow.js.

04

More than one error

The parser stops at the first syntax error. The document model blanks the offending line and reparses, so several errors surface at once.

05

Formatter is the emitter

Re-emitting a parsed AST yields the one canonical SFL text. Formatting reuses the emitter and refuses to run on broken documents.

06

One feature, one file

Each LSP capability lives in its own module under features/, so a focused change never needs the whole server in your head.

Two extensions, one document

vscode-sfl understands the text, vscode-sfl-preview draws it. They never call each other: both react to the same .sfl document, and installing either one installs both through the extension pack.

The preview does not use the language server. Selection sync and canvas edits work on the raw text (sflOwnerBlocks.ts and stickyflow.js patchers), so the preview keeps working even when the language server is busy or the document has syntax errors.

Inside vscode-sfl

Two processes. The extension host holds only the LanguageClient and the declarative contributions. The language server owns the document model, the feature providers and the parser.

A keystroke, step by step

What happens between typing a misspelled link target and seeing the red squiggle, and how a hover request reuses the same path.

01

Activation

Opening a .sfl file fires onLanguage:sfl. activate() creates a LanguageClient pointing at out/server/server.js over IPC (with --inspect=6009 in debug) and starts it.

src/extension.ts → activate()
02

Incremental sync

The server advertises TextDocumentSyncKind.Incremental. TextDocuments applies each change, so the server always holds the current text without re-sending the file.

src/server/server.ts → onInitialize()
03

Build the document model

buildDocumentModel(text) calls parse(). On an SflParseError it records the error, blanks that line (keeping line numbers stable) and retries, up to 50 times. The final AST goes through resolveDocument().

src/server/documentModel.ts → sfl-core/parser.ts → sfl-core/resolver.ts
04

Publish diagnostics

computeDiagnostics() maps parse errors by line and column, and resolver errors (unknown style, unresolved from:/to:, duplicates, inheritance cycles) by their precise range. Closing the file clears them.

server.ts → onDidChangeContent / onDidClose → features/diagnostics.ts
05

Answer a request

A hover, completion or rename request gets the model through modelForUri(), which reuses the one built for diagnostics as long as the document version hasn't moved. It hit-tests the cursor with queries.ts and answers. Hover pulls keyword docs from sflDocs.ts and a style's effective, inherited properties from the resolver.

server.ts → features/hover.ts → sfl-core/queries.ts + features/sflDocs.ts

Top level separates the client, the server and the declarative assets VS Code reads directly.

   ├─ server/

   │  └─ __tests__/         Vitest unit tests, no VS Code needed
   └─ test/                 Integration tests in a real VS Code instance

The two modules every request passes through.

sfl-core

A port of the SFL parser with source ranges added. When the grammar changes in stickyflow.js, the change has to be ported here by hand.

Design decisions

Trade-offs made deliberately, and what they cost.

D1

Copy, not import

Keeping a parser copy makes the extension self-contained and lets it track ranges the renderer never needs.

  • Cost: grammar changes need a manual port.
src/server/sfl-core
D2

Cache by document version

One model per file, rebuilt only when the LSP version changes. A keystroke used to trigger several full parses (diagnostics, completion, hover, outline); now it triggers one.

  • Cost: one model per open file stays in memory until the file closes.
src/server/server.ts
D3

Lexical colors only

Semantic tokens stay empty so highlighting matches the in-app editor exactly.

  • Cost: references and declarations look alike.
src/server/features/semanticTokens.ts

Quality checks

Unit tests exercise the language logic without VS Code. Integration tests prove the wiring.

Every fixture in fixtures/valid/ round-trips through parse and emit.
Diagnostics, hover docs, rename, references, symbols and formatting have focused Vitest suites.
npm run compile runs check:grammar: every block kind gets keyword highlighting.
npm run test:integration launches a real VS Code with the extension loaded.
Integration tests confirm activation and that the client actually talks to the server.
Run npm test for unit tests and npm run test:integration from a plain terminal (a leaked ELECTRON_RUN_AS_NODE=1 inside VS Code is the usual cause of failures).
